# Desenho: CI com lint e testes em cada PR (#18)

- **Ticket:** [#18](https://github.com/RafaelFerraz2002/senior-care-platform/issues/18)
- **Data:** 2026-11-10
- **Decisões de base:** ADR-001 (stack), ADR-004 (processo), ADR-005 (testes), ADR-006 (RGPD). Este desenho **aplica** essas decisões; não as muda.

## Porquê

Quem faz o merge não lê o código: confia nos testes, no CI e na descrição do PR. Até agora nada corre no GitHub, e um PR com o lint ou os testes partidos entrava sem ninguém dar por isso. Este ticket põe o GitHub Actions a verificar cada PR, com checks com nome que o #24 vai tornar obrigatórios.

## Objetivo

No fim:

- cada PR para o `main` corre os 7 checks do ADR-005 e a validação do título, todos em paralelo, em **10 minutos no máximo**;
- um PR falha se o lint, os tipos, os testes, a cobertura das linhas alteradas ou o tamanho das apps falharem;
- o PR tem um comentário fixo, o "Relatório do CI", com a cobertura e as exceções que o PR introduz;
- uma execução noturna sobre o `main` corre o e2e completo nos três browsers e verifica as dependências, e abre um issue quando falha.

**Não objetivos:**

- o ruleset que torna os checks obrigatórios e o `gitleaks` (#24);
- o deploy (#19);
- o teste de carga com k6 (ticket próprio);
- escrever testes de segurança: ainda não há tabelas. Só se prepara o sítio onde vão correr.

**Anti-objetivos:**

- um check que passa sem verificar nada sem o dizer (por exemplo, a cobertura a dar 100% porque não encontrou os ficheiros);
- um check que fica "à espera" num PR só de docs (ADR-004: nunca filtrar no gatilho);
- um workflow que dê acesso de escrita ou segredos a código de forks.

## Decisões

### 1. Âmbito

Tudo o que o ADR-005 passa para o #18 fica neste ticket: o CI dos PRs, a cobertura das linhas alteradas, o comentário com as exceções, a execução noturna e o issue automático. O ruleset e o `gitleaks` ficam no #24.

_Rejeitado:_ dividir em dois tickets. A parte noturna é um ficheiro a mais, e dividir contrariava a lista do ADR-005.

### 2. Workflows e checks

| Workflow                          | Gatilho                                                        | Jobs (= nomes dos checks)                                                                             |
| --------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `.github/workflows/ci.yml`        | `pull_request` para `main`; `workflow_dispatch`                | `lint-tipos`, `unitarios`, `integracao`, `seguranca`, `cobertura`, `e2e`, `tamanho-apps`, `relatorio` |
| `.github/workflows/titulo-pr.yml` | `pull_request` (`opened`, `edited`, `synchronize`, `reopened`) | `titulo-pr`                                                                                           |
| `.github/workflows/noturno.yml`   | `schedule` (todos os dias); `workflow_dispatch`                | `e2e-browsers`, `dependencias`                                                                        |

- Os nomes dos jobs são estáveis: o #24 vai referi-los no ruleset. Os 7 do ADR-005 e o `titulo-pr` vão ser obrigatórios; o `relatorio` não.
- Os jobs correm em paralelo, exceto o `cobertura`, que espera pelo `unitarios`, pelo `integracao` e pelo `seguranca`, e o `relatorio`, que espera pelo `cobertura`.
- **Nenhum filtro de caminhos (`paths`, `paths-ignore`) no gatilho** (ADR-004).
- O título valida-se num workflow à parte para que editar o título não volte a correr os testes.

_Rejeitado:_ um job único com vários passos. Dá um só check, e o #24 não consegue tornar cada parte obrigatória.

**O que corre cada job:**

| Job            | Corre                                                                                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lint-tipos`   | `pnpm lint` e `pnpm typecheck`                                                                                                                                            |
| `unitarios`    | `pnpm test` com cobertura; guarda os relatórios lcov como artefacto                                                                                                       |
| `integracao`   | `pnpm test:integration` com cobertura (Testcontainers, Docker do runner), **sem** os testes de segurança; guarda os relatórios lcov                                       |
| `seguranca`    | Só os testes `*.seguranca.test.ts` (decisão 3), com cobertura; guarda os relatórios lcov                                                                                  |
| `cobertura`    | Junta os lcov dos três jobs e corre o `diff-cover` (decisão 4)                                                                                                            |
| `e2e`          | `pnpm test:e2e` com os serviços do `docker compose` em pé, nos projetos do Playwright que já existem (`chromium` e `webkit-ipad`): Chromium e WebKit, como pede o ADR-005 |
| `tamanho-apps` | `pnpm build` e `pnpm check:size`                                                                                                                                          |
| `relatorio`    | Escreve o comentário fixo no PR (decisão 5)                                                                                                                               |
| `titulo-pr`    | Valida o título em Conventional Commits                                                                                                                                   |

- O `.env` do CI copia-se do `.env.example`: as credenciais lá são públicas e só servem para os serviços locais do runner.
- O Node vem do `.nvmrc` e o pnpm do campo `packageManager`.

### 3. Testes de segurança: `*.seguranca.test.ts`

- Os testes obrigatórios dos ADRs 002, 003 e 006 identificam-se pelo **sufixo do ficheiro** `.seguranca.test.ts`.
- Na API, vivem em `apps/api/test/`, ao lado dos de integração (ADR-005, secção 6), e correm com a configuração de integração (Postgres real). Quase todos os testes obrigatórios destes ADRs são da API.
- Se algum tiver de viver numa app ou num pacote, usa o mesmo sufixo e fica ao lado do código, como um unitário. O exemplo provável é o do ADR-006: o evento do Sentry enviado pelo browser não leva dados pessoais. O check `seguranca` corre-os também.
- Em todos os pacotes, a configuração dos testes normais exclui o sufixo `.seguranca.test.ts`, e só o check `seguranca` os corre.
- O `integracao` exclui-os e o `seguranca` corre só esses. Assim, cada teste corre uma vez e o GitHub mostra à parte que os de segurança passaram.
- Um teste de segurança com o nome errado não escapa: corre na mesma no `integracao`, só que fora do check `seguranca`.
- **Enquanto não houver nenhum**, o check passa e escreve no resumo do job "Ainda não há testes de segurança". Não pode ficar verde em silêncio.
- A convenção fica escrita no `CONTRIBUTING.md`.

_Rejeitado:_ uma pasta própria para os testes de segurança. Separava-os dos testes de integração do mesmo módulo, e o check já os mostra à parte.

### 4. Cobertura das linhas alteradas: `diff-cover`

- O `unitarios`, o `integracao` e o `seguranca` geram cobertura em lcov (Vitest com `@vitest/coverage-v8`). As linhas cobertas pelos testes de segurança também contam. Os testes de segurança têm de existir na mesma, seja qual for a percentagem (ADR-005).
- **Que ficheiros contam** (ADR-005, secção 4: a API, o `packages/shared` e a lógica das apps; fora ficam as páginas, as rotas, os componentes só visuais, o código gerado, as migrações e a configuração). Como o caminho sozinho não separa um componente visual da lógica, a regra aplica-se pela extensão:
  - **contam** os ficheiros `.ts` dentro de `src/` em `apps/api`, `apps/gestao`, `apps/registo`, `packages/shared` e `packages/fake-data`;
  - **não contam** os `.tsx` (páginas, rotas e componentes), o `packages/ui`, o `packages/api-client`, o código gerado (`*.gen.ts`), as migrações, os ficheiros de configuração, o `e2e/` e os `scripts/`;
  - por isso, **a lógica das apps (hooks, estado, a fila offline) vive em ficheiros `.ts`**, e os `.tsx` só desenham. Fica escrito no `CONTRIBUTING.md`. _Decisão minha._
  - A lista de ficheiros que contam vai no `coverage.include` do Vitest. Assim, um ficheiro novo sem nenhum teste aparece com 0% e não escapa à conta.
- O `cobertura` junta os relatórios e corre o `diff-cover` contra o `origin/main`, com o mínimo de **80%**. Abaixo disso, o check falha.
- A percentagem global aparece no relatório só como informação.
- Os caminhos dos ficheiros nos lcov têm de ser relativos à raiz do repositório, senão o `diff-cover` não os associa ao diff e a cobertura passa sem verificar nada (anti-objetivo). Um teste prova-o: um PR de teste com uma linha nova sem cobertura tem de pôr o check a vermelho (decisão 9). Um PR sem linhas que contem (por exemplo, só docs) passa.
- A versão do `diff-cover` fica fixada.

_Rejeitado:_

- **Codecov:** é um serviço externo que recebe dados do repositório e de cujo uptime o merge passa a depender.
- **Script nosso:** mais código para manter, para algo que o `diff-cover` já resolve.

### 5. Relatório do CI: um comentário fixo no PR

- O job `relatorio` mantém **um único comentário** no PR, atualizado a cada execução, com:
  - a cobertura das linhas alteradas e a global;
  - as **exceções introduzidas pelo PR**, só nas linhas acrescentadas do diff, cada uma com ficheiro e linha:
    - `v8 ignore`;
    - mudanças ao `app-sizes.json`;
    - vulnerabilidades ignoradas no `pnpm audit` (decisão 8);
    - testes desligados: `.skip`, `.todo`, `.fixme`;
    - `eslint-disable`;
    - `@ts-ignore` e `@ts-expect-error`.
  - Se não houver exceções, diz "Sem exceções".
- O `eslint-disable` e o `@ts-ignore`/`@ts-expect-error` não estão na lista do ADR-005, mas também são exceções a um check. _Decisão minha._
- O relatório só informa: não falha o PR. As exceções continuam a precisar de autorização (CLAUDE.md, ADR-005), e a autorização é o merge.
- A deteção das exceções é um script com testes unitários com nomes em português, que correm no `unitarios`.
- Num PR vindo de um fork, o token não pode escrever: o relatório vai só para o resumo do job, sem falhar.

_Rejeitado:_ pôr o relatório só no resumo do job. Fica escondido, e o ADR-005 pede que fique bem à vista.

### 6. Segurança do próprio CI

- O gatilho é `pull_request`, **nunca `pull_request_target`**, que corre código de forks com acesso de escrita.
- `permissions: contents: read` no topo de cada workflow. Só o `relatorio` tem `pull-requests: write`, e só o noturno tem `issues: write`.
- As actions de terceiros ficam fixadas pelo **SHA do commit**, com a versão num comentário. As do GitHub (`actions/*`) também.
- Não é preciso nenhum segredo.
- Os logs e os artefactos não podem ter dados pessoais (ADR-006). Hoje só há dados fictícios; a regra fica escrita para quando houver mais.

### 7. Velocidade

- O `unitarios`, o `lint-tipos` (a parte dos tipos) e o `integracao` usam `turbo run … --affected`: o Turborepo corre só os pacotes afetados pelo PR. A cache do Turborepo guarda-se entre execuções.
- O `lint` corre sempre no repositório inteiro, porque é rápido.
- O `e2e` e o `tamanho-apps` correm sempre. Hoje são rápidos; revê-se quando o CI passar dos 10 minutos (ADR-005).
- A cache do pnpm e a dos browsers do Playwright também se guardam.
- Um PR só de docs corre todos os checks e passam todos; o `e2e` e o `tamanho-apps` demoram o mesmo que num PR de código. Se isso pesar, filtra-se dentro do workflow, nunca no gatilho (ADR-004).
- O tempo do CI deste PR fica medido na descrição do PR.

### 8. Execução noturna

- Corre todos os dias às **03:00 UTC**: às 3h em Lisboa no inverno e às 4h no verão.
- O `e2e-browsers` corre o e2e completo em **Chromium, Firefox e WebKit**, mas **só se o `main` mudou** desde a última execução noturna com sucesso; senão termina com sucesso e di-lo no resumo. Os projetos de Firefox e WebKit de desktop acrescentam-se ao Playwright e só correm de noite.
- O `dependencias` corre todas as noites o `pnpm audit`. Falha com vulnerabilidades `high` ou `critical`; as `moderate` e `low` ficam só no log. _Decisão minha._
- Se uma vulnerabilidade `high` ou `critical` ainda não tiver correção, ignorar essa vulnerabilidade é uma **exceção a um check** e segue a regra do ADR-005. Fica registada na lista de ignoradas do pnpm (`auditConfig` no `pnpm-workspace.yaml`), com o motivo e uma data de revisão. Aparece no relatório do PR que a acrescenta, e o Claude nunca a acrescenta sem perguntar. Este ticket não ignora nenhuma: a lista começa vazia.
- **Se algum dos dois falhar**, abre um issue com a label `noturno` (ADR-005) e o link da execução. Se já houver um aberto com essa label, comenta nesse em vez de abrir outro.
- _Risco:_ o GitHub desliga os workflows agendados ao fim de 60 dias sem atividade no repositório. Fica escrito no `CONTRIBUTING.md`.

### 9. Prova de que o CI falha quando deve

- No próprio PR, faz-se um commit que parte o lint e um teste unitário e acrescenta uma linha de código sem teste. Confirma-se que o `lint-tipos`, o `unitarios` e o `cobertura` ficam a vermelho, e o commit reverte-se.
- Os links das duas execuções (vermelha e verde) ficam na descrição do PR.
- O squash merge apaga esses commits do `main`.

- ADR-004 (processo): a tabela das regras em vigor diz que não há checks; atualiza-se para dizer que os checks existem e passam a obrigatórios no #24. Um ADR aceite não muda de decisão, mas o estado atual pode atualizar-se.

## Fica para quem implementa

- Os nomes e a estrutura dos scripts (o do relatório, o de "o `main` mudou?") e onde ficam os testes desses scripts, desde que corram no `unitarios`.
- A action para o comentário fixo e para validar o título, ou `gh` e um script, desde que fixadas por SHA.
- A configuração do Turborepo para a cobertura e o `--affected`, e como o `fetch-depth` permite comparar com o `main`.
- Que serviços do `docker compose` o `e2e` sobe.
- Criar a label `noturno`, se ainda não existir.
